*Status: Raft and the hybrid logical clock are already present. Multi-node setup
would be tested and made available in the next release.*

Egres uses quorum based Raft replication to achieve node failure tolerance.
Each entry in the Raft log stores a hybrid logical clock timestamp generated by
the leader in a monotonically increasing order. Every replica applies that
timestamp to its own clock as it applies the raft log.

In a multi-node cluster (next release), the node you connect to would own the
session. A write arriving at a follower would forward it to the leader, who
would commit it through Raft, and return the commit timestamp back to the
follower to store it in the session. Any future reads can then be served
directly from the follower. The follower would block the read until it has
applied the log corresponding to the commit timestamp (typically milliseconds),
thus achieving read your write guarantee.

</figure>

zdb is well integrated with Raft replication. Instead of using its own
write-ahead log, it uses the Raft WAL. So, every replica sees the same updates
to its memtables and reads a write to the leader practically as soon as it
commits.

## Replicated Compactions

zdb also does something that's harder to find in open-source: **replicated
compactions.** With files on S3, a compaction is broken into 2 stages. First
stage runs the compaction, generates the files, uploads them to S3, and emits
a manifest update for zdb to apply.

That update is optionally announced to the cluster first, so other nodes can
fetch chunks of the new files and warm them up before they are needed. The
leader then proposes the manifest update through Raft. Note that the manifest
update only carries the file ids, not their content. The manifest update is
typically a delta containing namespace id, tree id, minus these file ids at one
level, plus these file ids at the next. Memtable flushes go through the same
updates, so the log holds every change to the forest structure in a serial
order.

As the Raft log is applied, the manifest update is applied to zdb with it,
resulting in an identical zdb forest across all replicas. Even the replicas
which didn't run the compaction, get the compacted forest.

<figure class="fig">
  <img src="../figures/zdb-replicated-compaction.svg" width="1000" height="526" alt="Replicated compaction: the leader hands an L0 to L1 compaction to a follower, the follower merges, uploads the new files to S3 and returns a manifest update, the leader proposes it through Raft, and all three replicas apply it and hold the same forest" loading="lazy" />
</figure>

This removes the need for every replica to run its own background
compactions, saving CPU and disk I/O. The leader can also hand compaction work
to any node in the cluster to spread the workload, savings its own resources,
which are even more precious.

Replicated compactions also makes bringing up a new replica on S3 cheap and
fast. The manifest is rebuilt from the log: fetch the last snapshot manifest,
apply the manifest updates since (recreating all the trees in zdb forest state),
and then apply only the writes that are still in memtables and not yet flushed
(recreating the memtables). This yields an identical zdb forest as all others,
which also makes query latencies predictable.
